## 1. Инструменты и зона ответственности каждого

Три библиотеки решают три **разные** задачи. Понимание границы между ними — половина
понимания кооперативного стека.

### FishNet — сетевой движок (репликация)

Отвечает на вопрос: «как состояние мира одинаково выглядит у всех участников».

Ключевые подсистемы, все живут компонентами на объекте `NetworkManager`:

| Подсистема | Что делает | Где используется в проекте |
|---|---|---|
| `NetworkManager` | корневой объект, создаёт и связывает остальные менеджеры | префабы `NetworkManager_Steam/_Lan` |
| `TransportManager` | держит активный транспорт, режет данные на пакеты, собирает батчи | префаб NetworkManager |
| `ServerManager` | приём подключений, спавн/деспавн, авторитет | `SessionCoordinator`, `SessionManager` |
| `ClientManager` | подключение к серверу, приём объектов | `SessionManager` |
| `TimeManager` | сетевые **тики** — общий дискретный шаг симуляции | `PlayerMotor` |
| `SceneManager` (`FishNet.Managing.Scened`) | синхронная загрузка сцен у всех участников | `SessionManager`, `SessionCoordinator` |
| `ObserverManager` | кому какой объект видно | по умолчанию (все видят всех) |
| `PredictionManager` | буферизация вводов, откат и пересимуляция | `PlayerMotor` |
| Кодогенерация (ILPostProcessor) | превращает `[ServerRpc]`, `[Replicate]`, `SyncVar<T>` в реальный сетевой код на этапе компиляции | все `NetworkBehaviour` |

Про кодогенерацию стоит сказать отдельно: FishNet — не рефлексия в рантайме. После
компиляции ваших сборок FishNet проходит по IL и **дописывает** методы сериализации,
регистрацию SyncVar'ов и обвязку RPC. Поэтому вызов `SetReadyServerRpc(true)` на клиенте
физически превращается в «записать аргументы в буфер и отправить», а на сервере —
в «прочитать, проверить владельца, вызвать тело метода». Отсюда же требование, чтобы
сборка ссылалась на `FishNet.Runtime` — иначе кодогенератор её не обработает.

### Facepunch.Steamworks — обёртка над Steamworks SDK

Отвечает на вопрос: «кто эти люди и как они находят друг друга».

Это C#-обёртка над нативным `steam_api64.dll`. Из всего Steamworks нам нужны:

| API | Зачем |
|---|---|
| `SteamClient.Init/Shutdown/RunCallbacks` | жизненный цикл соединения с клиентом Steam |
| `SteamClient.SteamId`, `SteamClient.Name` | личность игрока — бесплатно, без своего аккаунт-сервиса |
| `SteamMatchmaking` | создать лобби, войти, читать/писать метаданные, события участников |
| `SteamFriends.OpenGameInviteOverlay` | нативный диалог приглашения друзей |
| `SteamFriends.OnGameLobbyJoinRequested` | друг нажал «Присоединиться», пока игра запущена |
| `SteamApps.CommandLine` | игра запущена **по приглашению** (`+connect_lobby <id>`) |
| `SteamNetworkingSockets` | собственно P2P-транспорт (используется внутри FishyFacepunch) |

**Важная деталь про колбэки.** Steam отвечает асинхронно: `CreateLobbyAsync` не возвращает
лобби мгновенно, ответ приходит в очередь. Очередь нужно прокачивать. Есть два режима:

* `SteamClient.Init(appId, asyncCallbacks: true)` — Facepunch сам крутит фоновый цикл;
* `SteamClient.Init(appId, asyncCallbacks: false)` + ручной `SteamClient.RunCallbacks()`.

В проекте выбран **второй** ([`SteamService.cs`](../Assets/_Project/Scripts/Steam/SteamService.cs)):
`RunCallbacks()` вызывается один раз за кадр из `GameBootstrap.Update()`. Тогда все колбэки
Steam гарантированно приходят в главном потоке Unity между кадрами, и внутри обработчика
можно спокойно трогать `UnityEngine` API. С фоновым циклом это не гарантировано.

### FishyFacepunch — транспорт, склейка первых двух

Отвечает на вопрос: «как байты FishNet долетают через инфраструктуру Steam».

Это реализация абстрактного класса `FishNet.Transporting.Transport` поверх
`SteamNetworkingSockets`. Что он даёт:

* **адресация по SteamID64 вместо IP.** Клиент подключается не к `95.24.x.x:7770`,
  а к `76561198...`. IP хоста наружу не попадает вообще;
* **Steam Datagram Relay (SDR)** — если прямое P2P-соединение не устанавливается
  (симметричный NAT, CGNAT у мобильного оператора), трафик идёт через магистральные
  реле Valve. Это тот самый «просто работает без проброса портов», ради которого
  в кооп-играх и берут Steam;
* **шифрование и аутентификация** соединения средствами Steam;
* **специальный путь для хоста.** Когда сервер и клиент — один процесс, транспорт
  использует внутренний `ClientHostSocket`: данные хоста не уходят в сеть вообще.
  Это видно в логах: `Local client is starting for FishyFacepunch. Server IP is , port is 0`.

Обратная сторона: **нельзя подключиться к самому себе с одного аккаунта Steam**.
Именно поэтому в проекте есть LAN-режим — см. раздел 8.

## 2. Как эти три библиотеки соединяются

Точка стыковки ровно одна, и она умещается в две строки кода.

```
       Steam Matchmaking                         FishNet
   ┌──────────────────────┐              ┌────────────────────────┐
   │ Лобби (комната)      │              │ Сервер + клиенты       │
   │  • владелец          │              │  • спавн объектов      │
   │  • участники         │              │  • SyncVar / RPC       │
   │  • метаданные (k→v)  │              │  • сетевые сцены       │
   └──────────┬───────────┘              └───────────┬────────────┘
              │                                      │
              │  lobby.SetData("coop_host", steamId) │
              └──────────────────────────────────────┘
                       ClientManager.StartConnection(steamId)
```

**Хост** ([`SessionManager.HostAsync`](../Assets/_Project/Scripts/Networking/SessionManager.cs)):

1. `SteamMatchmaking.CreateLobbyAsync(4)` — комната создана, мы её владелец;
2. `ServerManager.StartConnection()` — поднялся сервер FishNet на транспорте FishyFacepunch;
3. `lobby.SetData("coop_host", мой SteamID64)` — публикуем «адрес» в метаданных лобби;
4. `ClientManager.StartConnection("127.0.0.1")` — хост подключается к себе же
   (адрес игнорируется, идёт через `ClientHostSocket`).

**Клиент** ([`SessionManager.JoinAsync`](../Assets/_Project/Scripts/Networking/SessionManager.cs)):

1. `SteamMatchmaking.JoinLobbyAsync(lobbyId)` — вошли в комнату;
2. читаем `lobby.GetData("coop_host")`;
3. `ClientManager.StartConnection(hostSteamId)` — FishNet передаёт строку транспорту через
   `Transport.SetClientAddress`, FishyFacepunch делает `SteamNetworkingSockets.ConnectRelay`.

Лобби на этом свою работу закончило: игровой трафик через него не идёт.

**Почему это важно архитектурно.** Единственная строка, знающая про Steam, — это формат
адреса. Всё остальное — `ILobbyService`. Заменить Steam на Epic Online Services или на
прямое IP — значит написать новую реализацию одного интерфейса; сетевой код не меняется
вообще. В проекте это не гипотеза: `LanLobbyService` — вторая рабочая реализация того же
интерфейса, и `SessionManager` не содержит ни одной ветки `if (steam)`.

## 3. Архитектура проекта

### Слои и направление зависимостей

Каждый слой — отдельная сборка (`.asmdef`). Это не украшение: asmdef физически
**запрещает** обратную зависимость, поэтому «случайно» вызвать Steam из геймплея нельзя.

```
Coop.Core        ← абстракции, конфиг, логгер. Не зависит ни от чего.
   ↑
Coop.Steam       ← Facepunch. Реализует ILobbyService и ILocalUser.
   ↑
Coop.Networking  ← FishNet. Сессия, спавн, профили игроков. Про Steam НЕ знает.
   ↑
Coop.Gameplay    ← движение, камера, внешний вид.
   ↑
Coop.UI          ← «глупые» вью.
   ↑
Coop.App         ← composition root: единственное место, где всё связывается.
```

Побочные плюсы разбиения: правка UI перекомпилирует одну маленькую сборку, а не весь
проект; сетевой слой можно покрыть тестами без Steam.

### Ключевые типы

| Тип | Роль |
|---|---|
| [`AppConfig`](../Assets/_Project/Scripts/Core/Config/AppConfig.cs) | ScriptableObject: AppId, число игроков, LAN-режим |
| [`ILobbyService`](../Assets/_Project/Scripts/Core/Sessions/ILobbyService.cs) | абстракция матчмейкинга |
| [`SteamLobbyService`](../Assets/_Project/Scripts/Steam/SteamLobbyService.cs) | реализация на Steam Matchmaking |
| [`LanLobbyService`](../Assets/_Project/Scripts/Networking/LanLobbyService.cs) | реализация «без матчмейкинга», прямой IP |
| [`SteamService`](../Assets/_Project/Scripts/Steam/SteamService.cs) | жизненный цикл Steam API + `ILocalUser` |
| [`SessionManager`](../Assets/_Project/Scripts/Networking/SessionManager.cs) | оркестратор: лобби ↔ транспорт, старт/стоп сессии |
| [`SessionCoordinator`](../Assets/_Project/Scripts/Networking/SessionCoordinator.cs) | серверная логика сессии, реплицируется клиентам |
| [`PlayerSession`](../Assets/_Project/Scripts/Networking/PlayerSession.cs) | профиль игрока: имя, цвет, готовность |
| [`PlayerMotor`](../Assets/_Project/Scripts/Gameplay/PlayerMotor.cs) | движение с предсказанием и реконсиляцией |
| [`GameBootstrap`](../Assets/_Project/Scripts/App/GameBootstrap.cs) | composition root |

### Сцены

| Сцена | Что в ней | Кто загружает |
|---|---|---|
| `Bootstrap` | только `GameBootstrap` | точка входа (индекс 0) |
| `MainMenu` | камера, Canvas, `MainMenuView` | Unity `SceneManager` (оффлайн) |
| `Lobby` | камера, Canvas, `LobbyView` | **FishNet** `SceneManager` (глобальная сетевая сцена) |
| `Game` | арена, точки спавна, камера с `PlayerCameraRig`, HUD | **FishNet** `SceneManager` |

Разделение «оффлайн-сцены грузим сами, сетевые — через FishNet» принципиально: сетевую
сцену обязан загружать сервер у всех сразу, иначе клиент получит объекты в сцену,
которой у него ещё нет.

## 4. Полный поток сессии, шаг за шагом

### 4.1 Запуск

`Bootstrap.unity` → `GameBootstrap.Awake()`:

1. **Steam инициализируется первым.** Порядок не косметический:
   `FishyFacepunch.Initialize()` сам зовёт `SteamClient.Init` и **бросает исключение**,
   если Steam не запущен, — это уронило бы весь `NetworkManager`. Инициализируя Steam
   заранее и с `try/catch`, мы либо получаем рабочий Steam (транспорт увидит
   `SteamClient.IsValid` и ничего делать не станет), либо узнаём о проблеме до создания
   `NetworkManager` и переключаемся на LAN.
2. Выбирается реализация `ILobbyService`: `SteamLobbyService` или `LanLobbyService`.
3. **`NetworkManager` создаётся из префаба, а не лежит в сцене.** Именно это даёт контроль
   над моментом его `Awake()`. Объект в сцене такой гарантии не даёт.
4. Создаётся `SessionManager`, ему явно передаются зависимости (`Construct(...)`).
5. Сервисы публикуются в `SessionServices` — единственный статический локатор в проекте
   (нужен потому, что UI живёт в других сценах и не может получить ссылки конструктором).
6. Грузится `MainMenu`. Все системы уже в `DontDestroyOnLoad`, поэтому переживут любую
   смену сцен.
7. Если игра запущена по приглашению (`+connect_lobby <id>` в командной строке) —
   сразу идём подключаться.

### 4.2 Хост создаёт игру

```
MainMenuView.OnHostClicked()
  └─ SessionManager.Host()
       ├─ lobby.CreateAsync(4)              → Steam: комната FriendsOnly
       ├─ ServerManager.StartConnection()   → FishNet: сервер поднят
       │    └─ [событие] SessionManager.HandleServerConnectionState
       │         ├─ спавн SessionCoordinator (IsGlobal)
       │         └─ SceneManager.LoadGlobalScenes("Lobby", ReplaceScenes = All)
       ├─ lobby.PublishHostAddress(SteamID64)
       └─ ClientManager.StartConnection("127.0.0.1")
            └─ [событие] клиент подключился
                 └─ SessionCoordinator: спавн PlayerSession для этого соединения
```

### 4.3 Приглашение друга

* **Игра у друга запущена.** Хост жмёт «Пригласить друзей» →
  `SteamFriends.OpenGameInviteOverlay(lobbyId)` → нативный оверлей Steam → друг нажимает
  «Присоединиться» → у него срабатывает `SteamFriends.OnGameLobbyJoinRequested` →
  `SessionManager.Join(lobbyKey)`.
* **Игра у друга не запущена.** Steam запускает её с аргументом `+connect_lobby <id>`.
  Колбэка не будет — игра ведь ещё не работала. Аргумент разбирает
  [`SteamLaunchArguments`](../Assets/_Project/Scripts/Steam/SteamLaunchArguments.cs).

Оба сценария надо поддерживать: реализовав только первый, вы получите классический баг
«приглашение работает, только если игра уже открыта».

### 4.4 Клиент входит

```
SessionManager.Join(lobbyKey)
  ├─ lobby.JoinAsync(lobbyKey)              → Steam: вошли в комнату
  ├─ адрес хоста уже есть?  → подключаемся
  └─ адреса ещё нет?        → ждём события HostAddressChanged
```

Второй случай — не теория, а гонка, которая реально случается: клиент может войти
в лобби раньше, чем хост успел записать метаданные. Поэтому подключение сделано
реакцией на событие, а не линейным кодом.

Дальше FishNet сам:

1. отдаёт клиенту список глобальных сцен и ждёт, пока тот их загрузит;
2. по завершении вызывает `SceneManager.OnClientLoadedStartScenes` на сервере;
3. `SessionCoordinator` спавнит для него `PlayerSession`;
4. клиент получает **все** уже существующие `PlayerSession` со всеми SyncVar'ами —
   поэтому список лобби у него сразу правильный, без единой строки «синхронизации при входе».

### 4.5 Старт матча

```
LobbyView → SessionCoordinator.RequestStartMatchServerRpc()      [клиент → сервер]
   сервер проверяет:  фаза == Lobby, отправитель == хост, все готовы
       ├─ _phase.Value = Playing                                  [SyncVar → всем]
       ├─ lobby.SetJoinable(false)
       └─ SceneManager.LoadGlobalScenes("Game", ReplaceScenes = All)
             └─ на каждого клиента: OnClientPresenceChangeEnd
                   └─ спавн PlayerCharacter в игровой сцене, владелец = это соединение
```

Обратите внимание: персонаж спавнится **не** на «клиент подключился», а на «клиент
реально оказался в игровой сцене». Это единственный надёжный триггер — он одинаково
корректно отрабатывает и для тех, кто ждал в лобби, и для опоздавших.

### 4.6 Возврат и выход

* «Вернуться в лобби» (только хост) → `RequestReturnToLobbyServerRpc` → загрузка `Lobby`.
  Персонажи деспавнятся **сами**: они были заспавнены в сцену `Game`, а её выгрузили.
  Никакого ручного кода очистки писать не нужно — это следствие правильного выбора сцены
  при спавне.
* «Выйти» → `SessionManager.Leave()`: сначала останавливается клиент, потом сервер
  (чтобы остальные получили корректный disconnect, а не таймаут), затем `lobby.Leave()`
  и возврат в меню.
* Обрыв связи, кик, падение хоста — всё приходит в тот же `Leave()` через
  `ClientManager.OnClientConnectionState → Stopped`. Один путь выхода вместо трёх.

## 5. Ключевые механизмы FishNet и как они использованы

### 5.0 Шпаргалка: кто где выполняется

Главный источник путаницы в сетевом коде: **класс один, а исполняется он в нескольких
процессах, играя там разные роли**. Ролей ровно три:

| Роль | Кто это | Что ей позволено |
|---|---|---|
| **Сервер** | процесс, поднявший `ServerManager` | менять мир: писать SyncVar, спавнить, менять сцены |
| **Клиент-владелец** | клиент, которому принадлежит объект (`IsOwner`) | читать ввод, отправлять `[ServerRpc]` |
| **Клиент-наблюдатель** | все остальные клиенты, видящие объект | только читать реплицированное состояние |

**Хост — это одновременно сервер и клиент-владелец в одном процессе.** Отсюда ощущение,
что «код выполняется дважды»: у хоста обе роли играет один и тот же экземпляр объекта.

#### Колбэки FishNet

| Колбэк | Сервер | Клиенты | Примечание |
|---|:---:|:---:|---|
| `OnStartNetwork` / `OnStopNetwork` | ✅ | ✅ | на хосте — **один** вызов; сюда общие подписки |
| `OnStartServer` / `OnStopServer` | ✅ | ❌ | здесь оформляется вся серверная логика |
| `OnStartClient` / `OnStopClient` | ❌ | ✅ | на хосте вызывается тоже (он клиент) |
| `OnOwnershipServer` | ✅ | ❌ | |
| `OnOwnershipClient` | ❌ | ✅ | владение приходит **позже** `OnStartNetwork` |
| `OnSpawnServer(conn)` | ✅ | ❌ | по вызову на каждого наблюдателя |

#### Флаги

| Проверка | Отвечает на вопрос |
|---|---|
| `IsServerInitialized` | «я сервер?» |
| `IsClientInitialized` | «я клиент?» |
| `IsOwner` | «этот объект мой?» |
| `Owner` | «чей это объект» (валиден и на сервере, и на клиенте) |
| `NetworkManager.IsHostStarted` | «в этом процессе сервер и клиент одновременно?» |

#### Способы передачи

| Механизм | Вызывается | Выполняется |
|---|---|---|
| `[ServerRpc]` | на клиенте | **на сервере** |
| `[ObserversRpc]` | на сервере | на всех клиентах-наблюдателях |
| `[TargetRpc]` | на сервере | у одного указанного клиента |
| `SyncVar.Value = x` | **только на сервере** | значение приезжает всем |
| `SyncVar.OnChange` | — | везде; **на хосте дважды**: `asServer = true`, затем `false` |
| `[Replicate]` | у владельца каждый тик | у владельца, на сервере и (при Enable Prediction) у наблюдателей |
| `[Reconcile]` | на сервере | применяется на клиентах |

#### Как читать код проекта

В сетевых классах (`PlayerSession`, `SessionCoordinator`) методы сгруппированы регионами
именно по этому признаку: `ВЕЗДЕ`, `ТОЛЬКО СЕРВЕР`, `ТОЛЬКО КЛИЕНТ`,
`ВЫЗЫВАЕТСЯ НА КЛИЕНТЕ → ВЫПОЛНЯЕТСЯ НА СЕРВЕРЕ`. Если непонятно, где работает метод —
достаточно посмотреть, в каком он регионе.

#### А можно физически разделить серверный и клиентский код?

В этом проекте — нет, и это не недоработка, а следствие топологии. Здесь **listen-server**:
хост одновременно и сервер, и игрок. Разнести код по разным сборкам невозможно, потому что
в процессе хоста нужны обе половины сразу.

Разделение имеет смысл только при переходе на **выделенный сервер**: тогда собирается
отдельный билд с `Server Build` (символ `UNITY_SERVER`), из него вырезается графика и ввод,
а клиентский код изолируется через `#if !UNITY_SERVER`. FishNet это поддерживает, но для
кооп-игры на Steam P2P выделенный сервер — лишняя инфраструктура и лишние деньги: там
хостом выступает один из игроков.

Практический вывод: разделяйте не сборки, а **зоны ответственности внутри класса** —
регионами, ранними `return`-проверками и понятными именами (`...ServerRpc`, `Server...`).


### 5.1 Server authority: кто имеет право менять мир

Базовое правило кооп-игры: **клиент ничего не меняет, клиент просит**.

```csharp
// Клиент: "хочу отметиться готовым"
public void SetReady(bool ready)
{
    if (!IsOwner) return;
    SetReadyServerRpc(ready);      // просьба
}

// Сервер: решает и реплицирует результат
[ServerRpc]
private void SetReadyServerRpc(bool ready) => _isReady.Value = ready;
```

`[ServerRpc]` по умолчанию требует владения объектом, и проверку делает **сервер**.
Чужой клиент не может изменить ваш профиль, даже если подделает пакет.

Там, где владельца нет (`SessionCoordinator` не принадлежит никому), используется
`[ServerRpc(RequireOwnership = false)]` — и тогда проверять отправителя обязаны мы сами:

```csharp
[ServerRpc(RequireOwnership = false)]
public void RequestStartMatchServerRpc(NetworkConnection sender = null)
{
    if (!IsHostConnection(sender)) return;   // sender подставляет FishNet, подделать нельзя
    if (!PlayerSessionRegistry.AllReady()) return;
    StartMatch();
}
```

Параметр `NetworkConnection sender = null` — специальный: FishNet заполняет его сам
на стороне сервера. Это идиома, которую стоит знать.

Ещё пример — санитизация данных от клиента. Ник берётся из Steam на клиенте (у сервера
его нет), но сервер обрезает длину и подставляет дефолт перед репликацией:

```csharp
[ServerRpc]
private void SubmitProfileServerRpc(string displayName, ulong platformId)
{
    _displayName.Value = SanitizeDisplayName(displayName);  // недоверенные данные
    _platformId.Value = platformId;
}
```

### 5.2 SyncVar против RPC: когда что

| | SyncVar | RPC |
|---|---|---|
| Это | **состояние** | **событие** |
| Новый клиент | получит текущее значение при спавне | пропустит навсегда |
| Пример из проекта | имя, цвет, готовность, фаза сессии | «начать матч», «я готов» |

Практическое правило: если опоздавший игрок должен это увидеть — SyncVar. Если это
однократное «дзинь» — RPC. Ошибка «сделал готовность через RPC» обнаруживается ровно
в тот момент, когда кто-то подключается пятым и видит пустой список готовности.

В FishNet 4 SyncVar — не атрибут, а поле-обёртка:

```csharp
private readonly SyncVar<bool> _isReady = new(false);
public bool IsReady => _isReady.Value;
_isReady.OnChange += HandleReadyChanged;   // (prev, next, asServer)
```

### 5.3 Сетевые сцены и глобальные объекты

`SceneManager.LoadGlobalScenes(new SceneLoadData("Game") { ReplaceScenes = ReplaceOption.All })`
делает довольно много:

* рассылает команду загрузки всем подключённым и всем, кто подключится позже;
* ждёт готовности каждого клиента;
* выгружает старые сцены (`All` — включая оффлайновые, то есть главное меню);
* восстанавливает observers и спавнит объекты сцены.

Ручного «все загрузились?» писать не нужно.

Проблема, которую это создаёт: смена сцен уничтожает всё, что в них было. А профиль
игрока (имя, цвет, готовность) обязан пережить переход «лобби → матч». Решение —
флаг **`IsGlobal`** на `NetworkObject`: FishNet переносит такие объекты в
`DontDestroyOnLoad` и показывает их всем клиентам. Он включён у `PlayerSession`
и `SessionCoordinator`, но **не** у `PlayerCharacter` — персонаж должен умирать вместе
со сценой.

### 5.4 Владение (Ownership)

```csharp
ServerManager.Spawn(session, connection);          // владелец = это соединение
ServerManager.Spawn(character, connection, scene); // + явная сцена
```

Владение даёт три вещи бесплатно: `IsOwner` на клиенте (кем управлять, чей ввод читать),
проверку `[ServerRpc]`, и автоматический деспавн объектов при отключении игрока.

Третий аргумент `Spawn(..., scene)` — то, благодаря чему персонажи исчезают сами при
выгрузке игровой сцены.

### 5.5 Тики: TimeManager

Сеть работает не в кадрах, а в **тиках** — фиксированном шаге симуляции (по умолчанию
30/сек), одинаковом у сервера и клиентов. Тик — это единица, в которой измеряется ввод,
предсказание и реконсиляция. Отсюда железное правило внутри сетевой симуляции:
`TimeManager.TickDelta`, никогда `Time.deltaTime`.

## 6. Клиентское предсказание движения

Самая содержательная часть проекта — [`PlayerMotor`](../Assets/_Project/Scripts/Gameplay/PlayerMotor.cs).

### Проблема

| Подход | Читерство | Отзывчивость |
|---|---|---|
| Клиент двигается сам и шлёт позицию | тривиальное: шли любую координату | идеальная |
| Клиент шлёт ввод и ждёт ответа | невозможно | +RTT к каждому нажатию (60–150 мс) |
| **CSP + реконсиляция** | невозможно | идеальная |

### Как работает CSP

1. Каждый тик владелец собирает `MoveData` — **ввод**, а не позицию — и вызывает метод
   с `[Replicate]`.
2. FishNet делает две вещи сразу: выполняет метод локально (клиент видит отклик мгновенно)
   и отправляет ввод серверу.
3. Сервер выполняет **тот же** метод с тем же вводом на том же номере тика. Его результат —
   истина.
4. Сервер отправляет назад состояние (`[Reconcile]`). Клиент сравнивает со своим состоянием
   в том же тике: совпало — ничего не делает; не совпало — откатывается к серверному
   и заново проигрывает все неподтверждённые вводы.

Всю машинерию (история вводов, определение расхождения, повторный прогон) делает FishNet.
От нас требуется соблюсти два правила.

**Правило 1. `[Replicate]` должен быть детерминированной функцией `(состояние, ввод)`.**
Метод вызывается повторно при пересимуляции прошлого, поэтому внутри нельзя:
`Time.deltaTime`, `Random`, чтение «живого» ввода, обращение к UI.

Отсюда, кстати, и существование отдельного `PlayerInputReader`: ввод читается в `Update`
и складывается, а в `Replicate` попадает уже снятый слепок за конкретный тик. Прыжок
буферизуется отдельно (`ConsumeJump`), потому что кадры идут чаще тиков и нажатие
между тиками иначе бы потерялось.

**Правило 2. `[Reconcile]` обязан содержать ВСЁ изменяемое состояние симуляции.**
У нас это позиция, поворот и вертикальная скорость. Забытое поле = рассинхрон, который
проявляется как необъяснимое дрожание персонажа.

```csharp
public struct MotorState : IReconcileData
{
    public Vector3 Position;
    public float Yaw;
    public float VerticalVelocity;   // забудьте это поле — и прыжки начнут «дёргаться»
    ...
}
```

### Частные приёмы, применённые в моторе

* **Рыскание камеры передаётся в `MoveData`.** Сервер должен превратить ввод «вперёд»
  в мировое направление точно так же, как клиент, а камера — вещь чисто клиентская.
  Не передав `Yaw`, вы получите рассинхрон при каждом повороте камеры.
* **`CharacterController` выключается на время телепорта в `Reconcile`** — он перехватывает
  запись в `transform.position`, и без этого коррекция просто не применится.
* **Экстраполяция чужих персонажей.** Данные чужого ввода приходят с задержкой RTT.
  Для тиков, данных по которым ещё физически не может быть (`ReplicateState.IsFuture()`),
  повторяется последний известный ввод — но не более одного тика вперёд, чтобы ошибка
  предсказания оставалась незаметной. Прыжок при этом не повторяется: «залипший» прыжок
  выглядит хуже, чем чуть более поздний.
* **Галка `Enable Prediction` на `NetworkObject` — обязательна.** Она включает не только
  предсказание, но и **пересылку состояний наблюдателям**: FishNet вычисляет
  `EnableStateForwarding` как `_enablePrediction && _enableStateForwarding`. Со снятой галкой
  владелец и сервер двигаются абсолютно корректно, а остальные клиенты не получают ни одного
  replicate/reconcile-пакета и видят чужого персонажа неподвижным. Ошибки при этом не возникает
  нигде — поэтому в `PlayerMotor.OnStartNetwork` стоит явная проверка с понятным сообщением.
  Поле `Graphical Object` при этом намеренно оставлено пустым: сглаживанием занимается
  отдельный `NetworkTickSmoother` (так же сделано в официальном демо FishNet).
* **`NetworkTickSmoother` на дочернем объекте графики.** Симуляция идёт 30 раз в секунду,
  экран рисуется 120+. Смузер интерполирует **визуал** между тиками, не трогая физику.
  Ключевой момент: сглаживается дочерний объект, а корень с `CharacterController` живёт
  строго по тикам. Смешаете — сломаете предсказание.
* **`_reconcileTickInterval`** позволяет слать состояние не каждый тик — прямой рычаг
  «трафик против точности».

## 7. Best practices: что сделано и почему

### Архитектурные

1. **Разделение матчмейкинга и транспорта.** Steam-лобби и сетевой транспорт — разные
   вещи, связанные одной строкой адреса. За абстракцией `ILobbyService` стоят две рабочие
   реализации, и `SessionManager` не содержит ни одного `if (steam)`.
2. **Однонаправленные зависимости, закреплённые asmdef.** Компилятор не даст сетевому слою
   узнать про Steam. Комментарий «так делать нельзя» — не работает, ошибка компиляции — работает.
3. **Composition root.** Все зависимости создаются и связываются в одном месте
   (`GameBootstrap`), явным `Construct(...)`. Единственный статический локатор
   (`SessionServices`) существует потому, что UI живёт в отдельных сценах, и это
   задокументировано, а не сделано «просто так».
4. **Humble View.** UI превращает клик в вызов метода и рисует состояние, о котором ему
   сообщили. Логику сессии можно тестировать без сцены.
5. **Конфигурация в ScriptableObject**, а не в константах: меняется без перекомпиляции,
   один источник правды для всех систем.
6. **Один путь выхода из сессии.** Штатный выход, обрыв, кик и падение хоста сходятся
   в `Leave()`. Три разных пути очистки — три разных набора багов.

### Сетевые

7. **Клиент просит, сервер решает.** Все изменения мира — через `[ServerRpc]` с проверкой
   на сервере.
8. **Данные от клиента считаются недоверенными.** Ник обрезается и валидируется сервером.
9. **Состояние — SyncVar, события — RPC.** Гарантирует, что опоздавший видит корректную картину.
10. **Состояние, которое должно совпадать у всех, приходит с сервера.** Даже цвет капсулы:
    сервер назначает индекс, клиенты его читают. Вычисляй клиенты цвет сами — рано или
    поздно разошлись бы.
11. **Спавн по факту присутствия в сцене** (`OnClientPresenceChangeEnd`), а не по факту
    подключения. Единственный вариант, корректный и для опоздавших.
12. **Спавн в конкретную сцену** — уборка при смене сцен получается бесплатно.
13. **Долгоживущее состояние — в `IsGlobal`-объектах**, короткоживущее — в сценных.
14. **Гонки обрабатываются событиями, а не «поспим и попробуем ещё раз».**
    Пример: адрес хоста может появиться позже входа в лобби.

### Инженерные

15. **Симметричные подписки.** Каждый `+=` имеет `-=` в парном методе
    (`OnStartServer`/`OnStopServer`, `OnEnable`/`OnDisable`, конструктор/`Dispose`).
    Для **статических** событий Facepunch это критично: без отписки после выхода из
    Play Mode остаётся подписка на объект прошлой сессии, и приглашение обрабатывается дважды.
16. **Сброс статики через `[RuntimeInitializeOnLoadMethod(SubsystemRegistration)]`** —
    режим «Enter Play Mode без перезагрузки домена» сохраняет статические поля между
    запусками, и без сброса второй запуск ведёт себя иначе первого.
17. **Никакого голого `async void`.** Асинхронные операции запускаются через `RunGuarded`,
    который логирует исключения. Иначе вместо ошибки получаешь молча зависший UI.
18. **Отсутствие платформы — штатная ситуация, а не исключение.** `SteamService.TryCreate`
    возвращает `bool` и текст ошибки для показа пользователю.
19. **Диагностический лог вырезается из релиза** через `[Conditional]` — вместе с аргументами
    и склейкой строк, то есть без затрат на GC.
20. **`MaterialPropertyBlock` вместо `renderer.material`** — не плодит копии материала на
    каждого игрока.
21. **Переиспользование строк списка в UI** вместо пересоздания иерархии на каждое изменение.
22. **Валидатор Build Settings** (меню `Coop → Validate Build Settings`). Забытая сцена
    в билде — классическая ошибка «в редакторе работает, в билде нет»; такие вещи должен
    ловить инструмент, а не чеклист.
23. **Флаги командной строки для автозапуска** (`-autohost`, `-autojoin`, `-lan`).
    Тестирование кооперативной игры требует двух процессов; кликать в двух окнах руками —
    медленно и невоспроизводимо.

## 8. Тестирование кооперативной игры

### Steam-путь (то, ради чего всё)

Нужны два компьютера и два аккаунта Steam (в друзьях друг у друга). Билд лежит
в `Builds/CoopDemo`, рядом с `.exe` обязателен `steam_appid.txt` со значением `480`.

`480` — это Spacewar, публичный тестовый AppId Valve. Для своей игры замените его на свой
в `AppConfig` **и** в поле `Steam App ID` на префабе `NetworkManager_Steam`.

### LAN-путь (один компьютер)

Через Steam P2P нельзя подключиться к самому себе одним аккаунтом. Для проверки логики
на одной машине включите `Force Lan Mode` в `AppConfig` — приложение поднимет
`NetworkManager_Lan` с транспортом Tugboat и `LanLobbyService`. Ровно так проверялся
этот проект: редактор в роли хоста, отдельный билд с
`-lan -autojoin 127.0.0.1` в роли клиента.

Полезное дополнение (не входит в проект): **ParrelSync** — держит зеркальную копию
проекта, чтобы запускать два редактора одновременно. FishNet знает про него и даже
определяет `PARRELSYNC` в своём asmdef.

### Что проверять в первую очередь

* подключение второго игрока во время матча (late join);
* выход клиента, выход хоста;
* обрыв связи (в LAN-режиме проще всего — убить процесс клиента);
* приглашение при запущенной и при незапущенной игре;
* поведение при закрытом Steam.

## 9. Грабли, на которые я наступил

Ошибки не выдуманные — все встретились при сборке этого проекта.

1. **`FishyFacepunch.Initialize()` бросает исключение, если Steam не запущен**, и роняет
   `NetworkManager` целиком. Лечится порядком инициализации: Steam поднимается в
   composition root до создания `NetworkManager`.
2. **Facepunch собран под net4.x.** С `Api Compatibility Level = .NET Standard 2.1` проект
   не соберётся. Нужен `.NET Framework`.
3. **Коллизия хешей сетевых префабов.** FishNet хранит спавнящиеся префабы в
   `DefaultPrefabObjects` и адресует их по хешу пути. Префабы, созданные скриптом, могут
   получить хеш `0`, и билд падает с `have the same assetPath hash of 0`.
   Лечится `Fish-Networking → Refresh Default Prefabs`.
4. **`NetworkBehaviour` уже имеет свойство `IsHost`** («на этой машине запущены и сервер,
   и клиент»). Своё свойство с тем же именем даёт предупреждение CS0108 и путаницу —
   в проекте оно называется `IsSessionHost`.
5. **Владелец назначается позже, чем вызывается `OnStartNetwork`.** Закэшировав «мой профиль»
   в момент регистрации, получаешь `null` навсегда. В `PlayerSessionRegistry.Local` это
   вычисляемое свойство, а `OnStartClient`/`OnOwnershipClient` дополнительно уведомляют UI.
6. **`ReplaceOption.All` выгружает и оффлайновые сцены.** Это ровно то, что нужно при
   переходе «меню → лобби», но системы обязаны быть в `DontDestroyOnLoad`.
7. **`CharacterController` игнорирует запись в `transform.position`**, пока включён —
   в `Reconcile` его нужно выключать на время коррекции.
8. **Снятая галка `Enable Prediction` = «клиент не видит чужого движения».** Самый коварный
   из списка, потому что не даёт ни ошибки, ни предупреждения: локально всё работает
   идеально, сервер считает позиции правильно, и только на чужом экране персонаж стоит
   столбом. Причина — `EnableStateForwarding => _enablePrediction && _enableStateForwarding`
   в `NetworkObject`: со снятой галкой серверный метод `Replicate_SendNonAuthoritative`
   выходит на первой же строке и наблюдателям не уходит ничего. Ловушка особенно легко
   срабатывает, когда префаб создаётся скриптом: `_enablePrediction` по умолчанию `false`.

## 10. Что делать дальше

Направления, в которых этот скелет расширяется до чего-то настоящего:

* **Аутентификация.** FishNet `Authenticator` — проверка версии сборки и Steam
  Auth Session Ticket (`SteamUser.GetAuthSessionTicket`) до того, как клиент получит
  игровые данные. Сейчас проверка версии сделана «мягко», через метаданные лобби.
* **Interest management.** `ObserverManager` + `HashGrid`: не слать игроку то, чего он
  не видит. На маленькой арене не нужно, на большой карте — обязательно.
* **Host migration.** Сейчас падение хоста завершает сессию. Полноценная миграция — большая
  задача: нужно переносить авторитетное состояние на нового владельца лобби.
* **Публичный матчмейкинг.** `lobby.SetPublic()` + `SteamMatchmaking.LobbyList` с фильтрами
  вместо приглашений только для друзей.
* **Lag compensation.** `RollbackManager` FishNet — откат коллайдеров в прошлое для честных
  попаданий, если появится стрельба.
* **Пул объектов.** `NetworkManager` умеет использовать `ObjectPool`; на десятках спавнов
  в секунду это заметно.
* **Тесты.** Сетевой слой отделён от Steam именно ради этого: `LanLobbyService`
  и фейковый `ILocalUser` позволяют гонять сессию в PlayMode-тестах.
